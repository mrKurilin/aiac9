# Памятка для нового разработчика: как ассистент работает с файлами

Документ описывает фактическое поведение ассистента при работе с файлами
проекта: путь запроса, доступные операции, реально действующие ограничения
чтения и записи, бюджет инструментов и обработку ошибок. Всё изложенное
основано на текущей реализации (`files.go`, `mcp.go`, `agent.go`, `main.go`,
`rag.go`) и подкреплено тестами (`files_test.go`, `main_test.go`).

Справочник по инструментам см. в `docs/file-tools.md`; архитектуру RAG — в
`docs/architecture.md`. Здесь фокус — на сквозном сценарии «пользователь →
агент → MCP-сервер → файловая система».

## 0. Как запускается ассистент

`main` (`main.go:39`) поддерживает два режима запуска:

- **Сервер MCP**: ровно три аргумента, первый `--project-mcp-server`
  (`main.go:40`) → `serveMCP(os.Args[2], os.Stdin, os.Stdout)` (`main.go:41`).
  Клиент поднимает его как дочерний процесс (`startMCP`, `mcp.go:44`).
- **Терминал**: обычный запуск `mrkai`, работает `run` (`main.go:52`).

Параметры окружения (`main.go:48`–`main.go:60`):

- `MRKAI_PROJECT_ROOT` — корень проекта; иначе текущий каталог (`os.Getwd`).
- `DEEPSEEK_MODEL` — по умолчанию `deepseek-chat`.
- `DEEPSEEK_BASE_URL` — по умолчанию `https://api.deepseek.com/chat/completions`.
- `DEEPSEEK_API_KEY` — обязателен для запросов к модели (`agent.go:44`).

## 1. Путь запроса от пользователя до результата

1. Пользователь вводит цель командой `/task ЦЕЛЬ` (или подсказку `/help ВОПРОС`).
   Разбор команд — в `run` (`main.go:52`), ветка `default`.
2. Режимы различаются префиксом: `task := strings.HasPrefix(line, "/task ")`,
   `project := strings.HasPrefix(line, "/help ")`.
3. Для любого запроса поднимается MCP-сервер `startMCP(ctx, root)`; он
   передаётся агенту как `a.mcp`, а признак `a.taskMode` соответствует `task`.
4. В `answer` выбирается system-промпт: в task-режиме — «выполняй задачу через
   MCP инструменты: сначала найди и прочитай файлы (обычно не меньше двух),
   затем анализируй; если цель требует изменения документации, сохрани
   Markdown через `file_write`» (`agent.go:109`).
5. Для `/help` срабатывает RAG: если индекс не загружен — строится
   (`agent.go:117`–`agent.go:124`), затем ищутся топ-3 фрагмента
   `a.search.search(question, 3)` (`agent.go:128`), и доказательства
   дописываются в system-промпт (`agent.go:130`–`agent.go:135`).
6. Агент запрашивает список инструментов: `a.mcp.listTools` (`agent.go:137`).
   Каждый инструмент получает алиас `mcp__project__<name>` и попадает в `routes`;
   определения уходят модели как `toolDefinition`.
7. Запускается цикл модели (`agent.go:156`). На каждом раунде вызывается
   `client.Complete` (`agent.go:171`).
8. Если модель вернула `ToolCalls` (`agent.go:175`), агент вызывает инструмент
   через `a.mcp.callTool` (`agent.go:187`) и добавляет результат сообщением
   `role:"tool"` с `ToolCallID` (`agent.go:199`).
9. `callTool` (`mcp.go:126`) на стороне клиента отправляет JSON-RPC `tools/call`.
10. На сервере `serveMCP` маршрутизирует вызов по имени инструмента
    (`mcp.go:218`) к функциям `gitBranch`/`projectList`/`projectRead`/
    `projectSearch`/`projectWrite` (`mcp.go:220`–`mcp.go:229`).
11. Финал: как только модель отвечает без tool-calls, её текст возвращается; при
    `/help` дополнительно печатаются уникальные источники.

Ключевая мысль: ассистент **сам** выбирает файлы и инструменты; конкретные
пути и запросы задаёт модель, а не пользователь напрямую.

## 2. Доступные операции

Инструменты объявлены в `serveMCP` (литерал `tools` — `mcp.go:166`–`mcp.go:172`):

| Инструмент | Назначение | Аргументы | Реализация |
|------------|------------|-----------|------------|
| `git_branch` | Текущая git-ветка проекта | нет | `gitBranch` (`mcp.go:245`) |
| `file_list` | Список файлов проекта | нет | `projectList` (`files.go:52`) |
| `file_read` | Прочитать файл проекта | `path` | `projectRead` (`files.go:88`) |
| `file_search` | Поиск строки по файлам проекта | `query` | `projectSearch` (`files.go:104`) |
| `file_write` | Создать/обновить Markdown в `docs` | `path`, `content` | `projectWrite` (`files.go:138`) |

Агент получает ровно эти 5 инструментов; это жёстко фиксируют тесты
(`files_test.go:18`, `main_test.go:172`).

Схемы аргументов (`mcp.go:167`–`mcp.go:171`): у `file_read` обязателен `path`;
у `file_search` — `query`; у `file_write` — `path` и `content`; `git_branch` и
`file_list` аргументов не принимают.

## 3. Ограничения чтения (реально действующие)

Общий барьер — `safeProjectFile(root, name, write)` (`files.go:12`), вызываемый
и при чтении, и при записи.

- **Запрет путей**: пустой путь, абсолютный путь, обратные слэши
  (`files.go:13`); выход за корень (`.` , `..`, `../…`, `files.go:17`–`files.go:19`).
- **Скрытые и «чувствительные» сегменты**: каждый сегмент пути проверяется циклом
  (`files.go:20`–`files.go:24`): сегмент, начинающийся с `.`, отклоняется, а
  остальные прогоняются через `safeDocName(part+".md")`. Поскольку к сегменту
  принудительно дописывается `.md`, для сегментов действуют только правила
  ведущей точки и «чувствительных» слов; «чувствительное» слово в любом сегменте
  (`secret`, `credential`, `password`, `token`, `private`, `apikey`, `api_key`)
  даёт ошибку «скрытый или чувствительный путь» — см. `safeDocName` (`rag.go:34`).
- **Расширения для чтения**: только `.md`, `.go`, `.txt` (`files.go:29`–`files.go:32`).
  Прочее → «тип файла не поддерживается».
- **Симлинки**: симлинк в цепочке каталогов запрещён (`files.go:42`); целевой
  объект должен быть обычным файлом (`files.go:46`).
- **Размер**: `projectRead` отклоняет файлы больше 64 КиБ (`64<<10`) —
  «файл слишком велик» (`files.go:97`).
- **`file_list`**: пропускает каталоги с ведущей `.`, а также `data`, `vendor`,
  `testdata` (`files.go:64`); учитывает только файлы, проходящие
  `safeProjectFile(..., false)` (`files.go:75`); лимит 200 файлов
  (`files.go:70`); результат отсортирован, пути через `/` (`files.go:84`);
  прерывается по контексту (`files.go:58`).
- **`file_search`**: длина запроса 2–100 символов (`files.go:105`);
  регистронезависимый `strings.Contains` (`files.go:120`); формат
  `имя:строка: текст` с обрезкой строки до 240 символов (`files.go:121`–
  `files.go:123`); не более 50 совпадений (`files.go:124`); при отсутствии —
  «Совпадений нет» (`files.go:129`); нечитаемые файлы молча пропускаются
  (`files.go:115`).

Практический вывод: по умолчанию ассистент **не видит** файлы вне `.md`, `.go`,
`.txt`, не читает скрытые и чувствительные пути, не следует по симлинкам и не
читает файлы крупнее 64 КиБ.

## 4. Ограничения записи (реально действующие)

- **Куда можно писать**: только `docs/*.md` (`files.go:26`–`files.go:28`).
  Любой другой путь/расширение → «запись разрешена только в docs/*.md»
  (`files.go:28`); каталог должен быть ровно `docs` (`filepath.Dir(clean) != "docs"`),
  поэтому `docs/sub/x.md` недоступен для записи.
- **Размер содержимого**: не более 64 КиБ (`files.go:144`) — «содержимое
  слишком велико».
- **Каталоги**: создаются через `MkdirAll` с правами `0700` (`files.go:147`).
- **Атомарность**: запись идёт во временный файл `.mrkai-*` (`files.go:151`),
  применяются права `0600` (`files.go:157`), затем замена через `os.Rename`
  (`files.go:172`); временный файл удаляется через `defer os.Remove`
  (`files.go:156`).
- **Отчёт**: возвращается строка `Сохранён <name>: было N байт, стало M байт`
  (`files.go:174`), по которой тест проверяет передачу результата модели
  (`files_test.go:31`).

Все ограничения безопасного пути из раздела 3 (скрытые сегменты, «чувствительные»
слова через `safeDocName`, симлинки, выход за корень) действуют и при записи.
Поэтому, например, `docs/secret.md` и `docs/token.md` недоступны для записи, хотя
формально лежат в `docs` — это подтверждает `main_test.go:28` (файл `token.md` не
индексируется) и `files_test.go:66` (отказ записи в `docs/secret.md`).

## 5. Бюджет инструментов и обработка ошибок

### Бюджет (важно!)

Константы `maxToolRounds = 32` и `maxToolCalls = 128` (`agent.go:96`–`agent.go:99`).
Цикл идёт от 0 до `maxToolRounds` включительно (`agent.go:156`), то есть модель
получает возможность вызвать инструменты, а затем — **отдельный** финальный
запрос без инструментов (`agent.go:160`–`agent.go:164`):

- при исчерпании раундов или вызовов `availableTools` становится `nil` и в
  сообщения добавляется system-инструкция «Бюджет инструментов исчерпан…»
  (`agent.go:161`–`agent.go:163`);
- если модель всё равно пытается вызвать инструмент при нулевом бюджете —
  ошибка «превышен бюджет MCP…» (`agent.go:176`–`agent.go:177`);
- превышение батча вызовов за раунд также даёт ошибку бюджета (`agent.go:176`);
- расход бюджета виден в диагностике: «Модель: запрос N/…; вызовов
  инструментов …» (`agent.go:169`) и «MCP: вызываю project.<name>» (`agent.go:189`).

Поведение бюджета покрыто `TestAgentToolBudget` (`files_test.go:130`): сценарии
`round_limit_summary`, `call_limit_summary`, `oversized_batch`,
`model_ignores_limit`.

### Обработка ошибок по слоям

**Сервер (`serveMCP`).**
- Неверные имя/аргументы инструмента → JSON-RPC ошибка `-32602`; неразборные
  `arguments` → `-32602`.
- Неизвестный инструмент → `-32602` «неизвестный инструмент»; неизвестный
  метод → `-32601`.
- Ошибка доменной функции (`safeProjectFile`, `projectRead`, `projectWrite`
  и т.д.) **не** превращается в JSON-RPC ошибку: возвращается нормальный
  результат с `isError: true` и текстом ошибки.

**Клиент (`callTool`, `mcp.go:126`).**
- Аргументы должны быть JSON-объектом, иначе «аргументы инструмента должны
  быть JSON объектом».
- Пустой `content` или не-`text` первый элемент → «MCP инструмент не вернул
  текст».
- При `isError: true` текст трактуется как ошибка и возвращается как `error`.
- Транспорт `call` (`mcp.go:72`): несовпадение `ID` → «неверный ID ответа MCP»;
  server-error оборачивается в «MCP <method>: <message>»; при отмене контекста
  дочерний процесс убивается.

**Модель (`deepSeekClient.Complete`, `agent.go:43`).**
- Пустой ключ → «задайте DEEPSEEK_API_KEY» (`agent.go:44`).
- Ошибка соединения → «ошибка соединения с моделью»; отмена контекста
  пробрасывается.
- Не-2xx → «модель вернула HTTP %d».
- Тело ограничено `2<<20` байт; пустой или неразборный ответ → «неверный ответ
  модели»; отсутствие `choices` → «модель не вернула ответ».

**Агент (`answer`, `agent.go:99`).**
- Ошибка вызова инструмента не рушит цикл: результат подменяется строкой
  «Ошибка инструмента: <текст>» и передаётся модели. Неизвестное имя алиаса →
  «Ошибка инструмента: неизвестное имя».
- Если MCP недоступен (`a.mcp == nil`) — работа идёт без инструментов.
- Пустой ответ модели без tool-calls → «модель вернула пустой ответ».
- Ошибки `listTools`/`Complete`/RAG-поиска прерывают `answer` и возвращаются
  наверх.

**CLI (`run`, `main.go`).**
- Ошибки выводятся как `Ошибка:` / `Ошибка MCP:` в `out` без паники процесса.

Важно для разработчика: ошибки уровня файловой безопасности приходят модели как
**данные** (`isError`), а не как сбой транспорта, — агент может их увидеть и
исправить план.

## 7. Чек-лист для изменений в файловых возможностях

Если меняете поведение работы с файлами, держите в синхроне:

1. `safeProjectFile` (`files.go:12`) — правила путей/расширений/симлинков;
   и `safeDocName` (`rag.go:34`) — список «чувствительных» слов.
2. Соответствующую доменную функцию: `projectList` (`files.go:52`),
   `projectRead` (`files.go:88`), `projectSearch` (`files.go:104`),
   `projectWrite` (`files.go:138`).
3. Объявление и схему инструмента в `serveMCP` (`mcp.go:166`) и её
   маршрутизацию (`mcp.go:218`).
4. System-промпт task-режима (`agent.go:109`), цикл агента (`agent.go:156`) и
   константы бюджета (`agent.go:96`).
5. Тесты: `files_test.go` (в т.ч. жёсткие `len(tools) != 5`, `files_test.go:18`)
   и `main_test.go` (`main_test.go:172`).
6. Документацию: этот файл, `docs/file-tools.md`, `docs/architecture.md`,
   `README.md`.
