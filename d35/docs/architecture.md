# Общая логика поиска и интерфейсы

Поиск туда-обратно по стране в `searchJourney` сохраняет готовые предложения `one_way=false` по стране и отдельно проверяет до восьми городов из дешёвых исходящих предложений. Затем добавляет комбинации двух отдельных билетов, сортирует по общей цене, убирает повторы и оставляет пять результатов. Пустой обратный кэш либо ошибка дополнительного поиска не удаляют уже найденные готовые билеты; отмена всегда прерывает операцию. Для явно разных городов прилёта и обратного вылета остаётся поиск двух отдельных билетов без внутренних перелётов. В журнале `journey.result` отдельно указан `ready_round_trip_count`.

`search_context.go` отделяет самостоятельный новый запрос маршрута от уточнений. Полный запрос с явным началом нового поиска очищает предыдущий контекст перед обращением к модели; поле new_search позволяет модели дополнительно обозначить новую поездку. Новый запрос без указания обратного билета получает one-way по умолчанию, с очисткой обратной даты, города вылета и длительности. Уточнение дат сохраняет текущий тип билета; явное переключение на одну сторону имеет приоритет. Правила применяются и после исправления плана. Признак new_search не сохраняется как условие следующего хода.

`trace.go` пишет JSONL-журнал с общими session_id, turn_id и call_id для связи входа пользователя, запроса модели, параметров HTTP, успешных ответов, распознанных условий, решений фильтров и окончательного ответа. Журнал общий для терминала и Telegram. HTTP-заголовки авторизации не передаются логгеру; настроенные ключи, известные форматы токенов, секретные присвоения и внутренние адреса дополнительно маскируются рекурсивно. reasoning_content и подобные поля исключаются; объяснения решений программы записываются отдельно. Тела HTTP-ошибок не читаются в журнал, ошибочные payload с success=false опускаются. Ответ справочника сокращён до счётчика, крупные события до безопасного preview с признаком truncated.

Запись защищена mutex, файл имеет права 600 и сбрасывается на диск после события. Ротация ограничена тремя файлами по 5 МиБ. Одна сессия использует свой идентификатор; после /reset журнал не удаляется. /log показывает путь и состояние записи. Ограничение: ротация рассчитана на один процесс на DATA_DIR; текст запросов и публичные предложения остаются в локальном файле и не загружаются во внешние сервисы самим логгером.

`journey.go` подбирает две независимые авиаперевозки для поездки с разными городами прилёта и обратного вылета. Дополнительное поле плана return_origin задаёт обратный город; для страны без конкретных городов подбираются подходящие пары. Код проверяет одну страну назначения, совместимость календарных дат, длительность и суммарный бюджет; выбирает до пяти самых дешёвых комбинаций просмотренного кэша. Участок между городами страны назначения не ищется и не включается в цену. Ссылки на оба билета выводятся отдельно, единая бронь не подразумевается. Условие страны передаётся в запрос провайдеру как destination, а не только применяется после получения общих дешёвых направлений.

Актуальные пределы: диапазон до двух лет; бюджет запросов — максимум из трёх и количества месяцев диапазона, по 100 записей. Каждый месяц проверяется до дополнительной пагинации. Лимит просмотра показывается динамически. Диагностика содержит количество полученных и подошедших записей.

Состояние условий хранится отдельно от сообщений assistant и копируется вместе с историей Telegram-сессии. В истории остаются фактические ответы и краткий статус поиска. Клиент принимает прежнюю обёртку conditions/reply и fenced JSON; при неверных типах один раз просит исправление. После повторной неудачи plan_recovery.go восстанавливает известные поля, сохраняет предыдущие ограничения и применяет однозначные уточнения дат и типа поездки. Поиск сопровождается перечнем применённых условий и предупреждением о неполном применении уточнения. Недостающие обязательные данные запрашиваются, сетевые ошибки не превращаются в результаты поиска.

Основной интерфейс — чат mrkai в терминале. Telegram — необязательный адаптер. Оба вызывают один и тот же метод Agent.answer: извлечение условий, уточнения, поиск, фильтрация и формирование результата не дублируются. Launcher mrkai запрашивает только недостающие ключи Travelpayouts и DeepSeek скрытым вводом; токен Telegram требуется только при явном выборе Telegram-адаптера.

`main.go` собирает зависимости, загружает справочник городов и запускает обычный терминал либо Telegram (`--telegram`). `agent.go` содержит Agent и HTTP-клиент DeepSeek. Модель получает текущую московскую дату, ограниченную подходящую к диалогу выборку мирового справочника, ограниченную историю с фактическими ответами и запрос, возвращает JSON с уточнением или условиями поиска. Все обращения к LLM проходят через Agent. Сырые ответы Aviasales и ссылки на билеты модели не передаются. После ошибочного распознавания параметров выполняется одна попытка автоматического исправления с конкретной причиной ошибки. История сохраняет реальный текст уточнения или ошибки программы; после поиска — краткий статус и условия.

`cities.go` сопоставляет названия с кодами городов и формирует выборку до 64 кандидатов для модели; приоритет получают точные названия и коды, затем совпадения начала слова для русских падежных форм; модель не должна самостоятельно угадывать IATA-коды аэропортов. `travel.go` загружает официальный справочник городов, разрешает внутренние и международные направления, сохраняет явный фильтр страны назначения, обращается к `prices_for_dates`, проверяет рубли и фильтрует каждую запись. Ответы API могут содержать ближайшие даты вместо запрошенных, поэтому даты, обратный билет, длительность, направление и бюджет проверяются повторно в коде. Для прямого рейса учитываются оба плеча. Ссылки разрешены только на HTTPS `www.aviasales.ru`; ответ строится программой, без генерации цен моделью. Диапазон вылета до 731 дней разбивается по месяцам: сначала запрашивается первая страница каждого месяца, затем оставшийся бюджет используется для продолжения пагинации. Даты каждой записи проверяются по исходному диапазону включительно. Лимит запросов зависит от числа месяцев, по 100 записей, вывод — пятью предложениями. Для месяцев сравниваются календарные даты отправления; длительность — разница локальных календарных дат, а не число часов в пути.

`telegram.go` реализует long polling, меню команд, отдельную историю для каждого личного чата, отмену, таймауты, ограничение параллелизма и частоты. 429 обрабатывается с `retry_after` и отменяемым ожиданием, временные ошибки polling — с задержкой до 30 секунд; 401/404/409 прекращают процесс. При изменении поколения сессии отменённая операция не меняет её историю. Текст отправляется без parse_mode, блоками до 1800 Unicode-символов, чтобы не превысить лимит Telegram даже с emoji.

Offset сохраняется атомарно до передачи сообщения обработчику. Это предотвращает повтор платного запроса после аварии, но сообщение, обработка которого прервана аварией или сетевой ошибкой отправки, может остаться без ответа: пользователь должен повторить запрос. Гарантии exactly-once нет. История и дневные лимиты не сохраняются на диск. При долгом отсутствии запусков Telegram может удалить старые updates; бот использует следующий offset согласно Bot API. Offset привязан к ID бота из getMe; при смене бота сбрасывается автоматически, поскольку update_id относится к конкретному боту.

Готовность требует успешной загрузки городов, getMe, проверки отсутствия webhook, проверки доступа Travelpayouts, регистрации команд и успешного getUpdates. Файл heartbeat обновляется только после успешного polling и удаляется в начале процесса. Docker healthcheck проверяет свежесть heartbeat; DeepSeek в readiness не вызывается, чтобы установка не тратила API-кредиты. Docker сам по себе не перезапускает контейнер только из-за статуса unhealthy: временные сбои обрабатываются polling, фатальные завершают процесс и срабатывает restart policy. За здоровьем и логами VPS следит администратор.

Установщик собирает образ с отдельным контекстом общего терминала. В контексты попадают только необходимые исходники; ключи вводятся после сборки. Приложение работает без root, файловая система контейнера read-only, данные находятся в отдельном Docker volume. При обновлении предыдущий контейнер сохраняется до успешной проверки нового. Образы старых версий автоматически не удаляются. Ошибка или прерывание установщика между остановкой старого контейнера и проверкой нового может требовать ручного запуска сохранённого контейнера; бесшовное обновление не реализовано.

Обязательны Agent, DeepSeek, Travelpayouts, общий терминал и Telegram-транспорт. Контекст чата нужен для уточнений. RAG, MCP, Ollama и старый release pipeline исключены: текущая задача их не требует.

Официальные протоколы: [Telegram Bot API](https://core.telegram.org/bots/api), [Aviasales Data API](https://support.travelpayouts.com/hc/ru/articles/203956163), [доступ к Data API](https://support.travelpayouts.com/hc/ru/articles/203956083), [DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode).

Международный поиск использует тот же prices_for_dates и существующий токен. Страна хранится в destination_country; для конкретного города проверяется согласованность страны и города, для любого направления предложения фильтруются по стране. Без страны и города поиск идёт по всему миру. География сама по себе не гарантирует наличие записей в кэше. Промежуточные аэропорты в данных этого метода отсутствуют, поэтому исключение определённого города пересадки не реализуется через фильтр direct: агент обязан отдельно сообщить ограничение и спросить согласие искать без него.
