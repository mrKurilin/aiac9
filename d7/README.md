# День 7 — агент с сохранением контекста

## Терминальный агент mrkai

Из каталога `aiac9/d7` запустите `./mrkai`. После установки команды в PATH
можно запускать `mrkai` из любого каталога. Нужны Go 1.21+ и переменная
`DEEPSEEK_API_KEY` в окружении терминала.

```sh
mrkai
mrkai -prompt 'Объясни, как работает контекст LLM'
mrkai -session study
```

Ответ выводится потоково, по мере получения фрагментов от DeepSeek (в том числе
с `-prompt`). В историю записывается только полностью полученный ответ.
В терминале оформляются заголовки, списки, цитаты, ссылки, жирный текст,
курсив и код. Для корректной обработки Markdown фрагменты собираются до конца
строки; последняя строка выводится при завершении ответа. При перенаправлении
в файл или pipe сохраняется исходный Markdown, фрагменты выводятся сразу.
`NO_COLOR=1 mrkai` отключает оформление. Таблицы и сложная вложенная разметка
сохраняются в текстовом виде; подсветка синтаксиса кода не выполняется.
Один запрос вводится одной строкой. `/reset` очищает память текущего диалога,
`/exit`, `/quit`, Ctrl+D или Ctrl+C завершают программу.
История сохраняется в `aiac9/d7/data/terminal.json`; `-session` выбирает отдельный
диалог (1–64 латинских букв, цифр, дефисов или подчёркиваний).
`DATA_DIR` позволяет выбрать другой каталог. Не запускайте два процесса с одним
именем сессии одновременно: они могут перезаписать историю друг друга.

Терминальный режим использует `deepseek-v4-flash` по умолчанию; модель можно
изменить через `DEEPSEEK_MODEL`. Формат запросов соответствует
[документации DeepSeek](https://api-docs.deepseek.com/).
Также доступны `go run . -cli` и `go run . -prompt 'Привет'`.
Обычный `go run .` запускает веб-чат.

Локальная проверка без обращений к API: `go test ./...` и `go vet ./...`.

Веб-чат из дня 6 научился помнить разговор между запусками. Историю каждого диалога агент хранит в JSON-файле на диске и подгружает её при старте, поэтому после перезапуска сервера разговор продолжается с того же места, как будто агент не выключался.

## Практики, которые мы применили, и почему

Вторая неделя курса — про внутреннее устройство агентов. Ключевая мысль лекции: **у LLM нет встроенной памяти**. Каждая новая сессия стартует с чистого листа, а «воспоминания» — это данные, которые платформа хранит снаружи и заново подмешивает в контекст. День 7 — это ровно про это: мы вынесли историю диалога из оперативной памяти процесса в долговременное хранилище.

| Практика | Как реализовано | Почему |
| --- | --- | --- |
| Разделение кратко- и долговременной памяти | В оперативной памяти живёт активная история (`Agent.history`), на диске — её постоянная копия через `Store` | Лекция, раздел «Memory management»: short-term memory удобна для работы, но без long-term memory агент забывает всё между запусками. Диск — самый простой вид долговременной памяти |
| Долговременная память — JSON-файлы | Одна беседа = один файл `<id>.json` в каталоге `DATA_DIR`, в нём массив сообщений | Задание допускает «JSON или SQLite». JSON выбран потому, что это стандартная библиотека Go (ноль зависимостей, `go 1.21`), файлы читаются человеком и их легко отлаживать, бэкапить и чистить. SQLite/Postgres/векторная БД понадобятся, когда бесед станет много или понадобятся запросы к истории |
| Зависимость от абстракции, а не от конкретного хранилища | Агент работает с интерфейсом `Store{Load, Save}`, а не с файлами | То же, что мы уже делали для модели через `ChatClient`: реализацию (JSON → SQLite → векторная БД) можно поменять, не трогая логику агента. Это продолжение архитектуры дня 6 |
| Атомарная запись | Файл пишется во временный файл, затем `fsync` и `rename` поверх целевого | Если процесс упадёт посреди записи, `rename` оставит либо старый, либо новый файл целиком — никогда не «полуобрыв». Полузаписанная история превратила бы диалог в мусор |
| Сохранение после каждого успешного обмена | Сообщения пишутся на диск сразу после удачного ответа модели | Любой сбой в этот момент теряет максимум один незавершённый обмен, а не весь диалог. При этом **неудачные** вызовы API в историю не попадают — память не отравляется мусором |
| Восстановление контекста по id беседы | Кука `d7_session` хранит id диалога; при старте агент создаётся с этим id и подгружает его историю | После рестарта in-memory-карта агентов пуста, но id в куке браузера сохраняется. Используя его, новый агент находит свой файл и продолжает разговор. Мы не генерируем новый случайный id, если кука уже есть |
| Сессии изолированы | У каждого браузера своя беседа, свой файл, общий мьютекс защищает от гонок | Разные пользователи не перемешивают память; конкурентные запросы одного пользователя сериализуются |
| Устойчивость к повреждённому файлу | Если файл истории не читается, агент пишет предупреждение в лог и начинает с чистого листа | Сервер не падает и остаётся доступным, даже если файл испортили вручную или при ручном редактировании |
| Конфигурация через окружение | Токен и настройки приходят из переменных окружения | Секрет не попадает в исходники и в Git; это же позволяет менять `DATA_DIR` на сервере без пересборки |

### Что мы сознательно не делаем (и что из лекции пригодится дальше)

Мы храним историю целиком и отправляем модели весь контекст. Для учебного чата этого достаточно, но у окна контекста есть предел. Из лекции: когда разговор разрастётся, понадобится одно из:

- **sliding window** — слать модели только последние N сообщений, чтобы контекст не рос бесконечно;
- **history compression** — свёртка старой части диалога в summary (лекция напоминает: сжатие теряет детали, это «неизбежное зло»);
- **векторная память / embeddings** — вместо всей истории подмешивать только релевантные фрагменты;
- **смена формата на TOON** — экономия токенов на повторяющихся структурах.

## Запуск на macOS или Linux

1. Перейдите в каталог проекта:

   ```bash
   cd /путь/к/AiAdventChallenge-9/aiac9/d7
   ```

2. Передайте токен и пароль для посетителей:

   ```bash
   export DEEPSEEK_API_KEY='sk-ваш_токен'
   export CHAT_PASSWORD='длинный-случайный-пароль'
   ```

3. Запустите агента:

   ```bash
   go run .
   ```

4. Откройте <http://localhost:8080>. Логин может быть любым, пароль — значение `CHAT_PASSWORD`.

История сохраняется в каталог `./data` относительно места запуска. Задать другой каталог можно переменной `DATA_DIR`.

## Проверка сохранения контекста на практике

1. Начните диалог: спросите что-нибудь, что агент должен запомнить, например: *«Меня зовут Антон»*.
2. Остановите сервер (`Ctrl+C`) и запустите его снова той же командой.
3. Продолжите тот же диалог в том же браузере: *«Как меня зовут?»* — агент ответит правильно.

Посмотреть, что именно сохранилось, можно в файле истории:

```bash
cat data/*.json
```

Кнопка «Новый диалог» очищает историю текущего браузера и тоже сохраняет это на диск: после перезапуска старый диалог не «воскреснет».

## Проверка без расходования токенов

Проект собирается и проходит статическую проверку без сети:

```bash
go vet ./...
```

Чтобы проверить механику сохранения локально, не тратя токены, укажите `DEEPSEEK_BASE_URL` на совместимый тестовый сервер (см. «Настройки»).

## Практика: запуск в этом окружении и доступ снаружи

Раздел собран по факту поднятия сервера в учебной VM за NAT (Go не был предустановлен, внешний IP — только у шлюза провайдера).

### 1. Подготовка

```bash
# Go нужен 1.21+. Если его нет:
sudo apt-get install -y golang-go
go version

cd d7
go vet ./...            # статическая проверка без сети
go build -o d7 .        # бинарник; index.html вшивается через //go:embed
```

### 2. Ключ и пароль — так, чтобы сервер их увидел

Процесс сервера читает ключ из окружения и завершается, если `DEEPSEEK_API_KEY` не задан. Нюанс: `export`, сделанный в интерактивном терминале **после** запуска сессии, не доходит до неинтерактивных оболочек (например, когда сервер стартует из менеджера задач). Надёжнее держать секреты в файле режима `600` и подставлять при запуске:

```bash
printf 'export DEEPSEEK_API_KEY=%q\n' 'sk-ваш_токен' > ~/.d7.env
printf 'export CHAT_PASSWORD=%q\n'   'длинный-случайный-пароль' > ~/.d7.pass
chmod 600 ~/.d7.env ~/.d7.pass
```

### 3. Локальный запуск

```bash
cd d7
set -a; . ~/.d7.env; . ~/.d7.pass; set +a
ADDR=127.0.0.1:8080 DATA_DIR="$PWD/data" ./d7
```

Проверка (без пароля сервер отвечает `401`):

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/                       # 401
curl -s -u chat:"$CHAT_PASSWORD" -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/   # 200
curl -s -u chat:"$CHAT_PASSWORD" -H 'Content-Type: application/json' \
  -d '{"message":"привет"}' http://127.0.0.1:8080/api/chat
```

### 4. Доступ снаружи, когда хост за NAT

Прямых входящих портов нет — публиковать чат можно только **исходящим туннелем**. Сервер при этом оставляем слушать `127.0.0.1`, наружу пробрасывает туннель. Перед публикацией обязателен `CHAT_PASSWORD`.

Проверенный вариант — localhost.run (без аккаунта, HTTPS на стороне сервиса):

```bash
ssh -o ServerAliveInterval=20 -R 80:localhost:8080 nokey@localhost.run
```

Сервис печатает адрес вида `https://<случайное>.lhr.life` — это и есть публичный URL чата (логин любой, пароль из `CHAT_PASSWORD`). URL **временный**: меняется при каждом переподключении/перезапуске туннеля.

Почему не Cloudflare quick tunnel (`cloudflared tunnel --url http://127.0.0.1:8080`): в части сетей он регистрирует соединение, но публичный адрес стабильно отдаёт `530/1033` — проверено в этом окружении, это не чинится со стороны клиента. Если нужен постоянный адрес — именованный туннель Cloudflare с аккаунтом, ngrok с authtoken или «forever-free»-домен на localhost.run.

Для постоянного сервиса на VM (автозапуск, переживание перезагрузок) используйте `systemd` из следующего раздела, а наружу — тот же туннель или обратный прокси с TLS.

## Запуск на виртуальной машине

Сервер не привязан к локальной машине — это обычный Go-бинарник. Чтобы чат жил на VM постоянно, а не в окне терминала, используйте `systemd`.

### 1. Соберите и загрузите на VM

Соберите бинарник под Linux (архитектура — под вашу VM, обычно `amd64`):

```bash
cd /путь/к/AiAdventChallenge-9/aiac9/d7
GOOS=linux GOARCH=amd64 go build -o d7 .
```

Загрузите на VM только бинарник `d7`. Файл `index.html` уже вшит в него через `//go:embed` на этапе сборки, поэтому на сервере он не нужен: любые правки интерфейса требуют пересборки бинарника, а не замены html. Разместим бинарник в `/opt/aiac9/d7`.

### 2. Создайте пользователя, каталог данных и файл с секретами

```bash
sudo useradd --system --home /opt/aiac9/d7 --shell /usr/sbin/nologin d7
sudo mkdir -p /var/lib/d7
sudo chown d7:d7 /var/lib/d7
sudo touch /etc/d7.env && sudo chmod 600 /etc/d7.env
sudo nano /etc/d7.env
```

Содержимое `/etc/d7.env`:

```bash
DEEPSEEK_API_KEY="sk-ваш_токен"
CHAT_PASSWORD="длинный-случайный-пароль"
DATA_DIR="/var/lib/d7"
ADDR="127.0.0.1:8080"
```

Правила формата файла: одна переменная на строку, без пробелов вокруг `=`, значения лучше брать в двойные кавычки. Если в значении есть `#`, `$`, пробелы или кавычки — без двойных кавычек `systemd` их не поймёт. `DATA_DIR` указываем на постоянный диск (не на tmpfs), чтобы история переживала перезагрузки VM.

### 3. Опишите службу

Создайте `/etc/systemd/system/d7.service`:

```ini
[Unit]
Description=DeepSeek chat agent (day 7)
After=network-online.target
Wants=network-online.target

[Service]
User=d7
Group=d7
WorkingDirectory=/opt/aiac9/d7
EnvironmentFile=/etc/d7.env
ExecStart=/opt/aiac9/d7/d7
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target
```

Включите и запустите:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now d7
sudo systemctl status d7
```

С этого момента чат переживает перезагрузки VM сам: `systemd` поднимет его, а история будет восстановлена из `/var/lib/d7`.

### 4. Доступ через HTTPS

Служба слушает `127.0.0.1:8080` — наружу её выставляет обратный прокси с TLS (Caddy, nginx) или Cloudflare Tunnel. Публиковать сервер наружу без `CHAT_PASSWORD` нельзя: посторонние смогут отправлять запросы за ваш счёт.

Обновление кода: пересоберите бинарник, положите его поверх и выполните `sudo systemctl restart d7` — диалоги не потеряются, потому что они в `/var/lib/d7`.

Бэкап памяти = копия каталога `/var/lib/d7` (например, ежедневная задача `cron`). Восстановление — распаковать файлы обратно в тот же каталог.

## Типичные проблемы и их решение

| Симптом | Причина | Решение |
| --- | --- | --- |
| При запуске: `переменная DEEPSEEK_API_KEY не задана` | Токен не попал в окружение процесса | Экспортируйте переменную в **том же** окне терминала, где запускаете `go run .`; на VM проверьте файл `/etc/d7.env` и что служба перезапущена после правки |
| При запуске: `address already in use` | Порт 8080 уже занят другой программой | Задайте другой порт: `ADDR=:8090 go run .` (macOS) или впишите `ADDR="127.0.0.1:8090"` в env-файл и `sudo systemctl restart d7` |
| Браузер просит логин и пароль | Включён `CHAT_PASSWORD` | Логин — любой, пароль — значение `CHAT_PASSWORD`. Если пароль не нужен — не задавайте `CHAT_PASSWORD` (только для локального запуска) |
| API отвечает `HTTP 401` | Неверный токен DeepSeek | Проверьте значение `DEEPSEEK_API_KEY`, перевыпустите ключ в кабинете |
| API отвечает `HTTP 402` | Закончился баланс API-аккаунта | Пополните баланс на <https://platform.deepseek.com> |
| Запрос висит или сетевые ошибки | Нет доступа к `api.deepseek.com` | Проверьте интернет, VPN/прокси, DNS; `curl -I https://api.deepseek.com` |
| После перезапуска агент «забыл» диалог | Другая кука (новый браузер/инкогнито) или другой `DATA_DIR` | Продолжайте диалог в том же браузере и профиле; запускайте с тем же `DATA_DIR`, что и при записи. История в `data/*.json` — проверьте, что файл появился |
| Сервер запущен, но страница не открывается с другой машины | Служба слушает только `127.0.0.1` | Это нормально, если снаружи стоит обратный прокси/туннель. Для прямого доступа задайте `ADDR=":8080"` и откройте порт в файрволе (не публикуйте без `CHAT_PASSWORD`) |
| На VM служба не стартует | Ошибки прав или формата env-файла | `sudo journalctl -u d7 -n 50` — читайте лог; бинарник должен исполняться пользователем `d7`: `sudo chmod 755 /opt/aiac9/d7/d7`; каталог данных должен принадлежать `d7`: `sudo chown -R d7:d7 /var/lib/d7` |
| На VM правки интерфейса не применились | `index.html` вшит в бинарник | Правьте `index.html` на своей машине и пересобирайте: `GOOS=linux GOARCH=amd64 go build -o d7 .`, затем снова загрузите бинарник и `sudo systemctl restart d7` |

## Настройки

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `DEEPSEEK_API_KEY` | — | Токен DeepSeek, обязателен |
| `CHAT_PASSWORD` | — | Пароль HTTP Basic Auth; обязателен для публичного доступа |
| `DATA_DIR` | `./data` | Каталог, где хранятся JSON-файлы истории диалогов |
| `DEEPSEEK_MODEL` | `deepseek-chat` | Модель, например `deepseek-reasoner` |
| `DEEPSEEK_BASE_URL` | `https://api.deepseek.com/chat/completions` | Endpoint; удобно для тестового совместимого сервера |
| `AGENT_SYSTEM_PROMPT` | «Ты полезный ассистент…» | Системная инструкция агенту |
| `ADDR` | `:8080` | Адрес веб-сервера |

## Структура

- `main.go` — запускает HTTP-сервер и открывает хранилище истории;
- `store.go` — интерфейс `Store` и реализация `JSONFileStore` (чтение, атомарная запись);
- `agent.go` — агент, клиент DeepSeek API; загрузка истории при создании и сохранение после каждого обмена;
- `web.go` и `index.html` — API, сессии, авторизация и интерфейс чата.

Если API отвечает `HTTP 401`, проверьте токен. При `HTTP 402` проверьте баланс. Если после перезапуска агент «забыл» диалог — убедитесь, что браузер сохранил куку `d7_session` и что `DATA_DIR` при запуске тот же, что и при прошлой записи.
